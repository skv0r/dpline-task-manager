# 002. HTTP-фреймворк api: Fastify (Prototype); Nest — позже отдельным сервисом

Дата: 2026-08-01  
Статус: **accepted**  
Связанные issues: [#34](https://github.com/skv0r/dpline-task-manager/issues/34), follow-up CRUD [#38](https://github.com/skv0r/dpline-task-manager/issues/38); родитель [#33](https://github.com/skv0r/dpline-task-manager/issues/33)

## Контекст

Фаза 1 (Prototype Cycle): нужен осмысленный HTTP-слой в `apps/api` вместо тонкого `node:http`. Сейчас — `GET /health`, dotenv из корня, порт **3001**, пакет `@dpline/api`.

Ограничения и приоритеты выбора (2026-07-27):

1. Рынок / учёба (уметь то, что встречается в стартапах).  
2. Скорость до рабочего CRUD.  
3. Не раздувать инфраструктуру.  
4. Nest как **целевой** стек позже — но не rewrite «на месте» в Фазе 1.  
5. Практика Fastify отдельно («prac time»), не только теория.

Auth, дизайн, tRPC — **вне** этой ADR.

## Критерии выбора (упорядочены)

1. Достаточно рынка и документации для учёбы.  
2. Быстрый путь к REST CRUD + валидации.  
3. Ясные слои без «магии фреймворка» на день ноль.  
4. Сохраняем `/health`, root `.env`, порт 3001.  
5. Честный путь к Nest без переписывания того же дерева файлов.

## Варианты

### A. Оставить thin `node:http`

Плюсы: ноль зависимостей.  
Минусы: вручную роутинг, валидация, логи, плагины; плохо масштабируется к CRUD и тестам.  
**Отклонено** как долгосрочное ядро.

### B. NestJS сразу

Плюсы: DI, модули, типичный корпоративный/стартап-бэкенд; цель на Фазе 2+.  
Минусы: выше порог и объём boilerplate для Prototype; откладывает «пощупать HTTP» на Fastify.  
**Отложено** — см. решение ниже (не rejected навсегда).

### C. Fastify 5.x ← **выбрано (Prototype)**

Плюсы: быстрый старт, plugins, логи **pino** из коробки, экосистема Zod/валидации, хорошая встречаемость.  
Минусы: меньше «батареек», чем у Nest; к Фазе 2 понадобится переезд.

### D. Express / Hono / другие

Не рассматривались всерьёз: Express — устаревший baseline для нового проекта; Hono — ок для edge, не наш фокус обучения.

### E. tRPC на Фазе 1

**Отклонено.** REST. tRPC можно поднять отдельным ADR позже, если появится нужда.

## Решение

**На Prototype (Фаза 1): Fastify (5.x), ESM, REST.**

Структура каталогов (зафиксировать сейчас; код — в #37–#38):

```text
apps/api/src/
  app.ts                 # create Fastify, plugins, listen
  routes/                # HTTP: method, path, status; тонкий слой
  services/              # бизнес-правила без req/res
  db/                    # Prisma client / доступ к БД
  schemas/               # Zod (вход/выход) — по мере CRUD
```

Поток: **route → service → db**.

Валидация и «как в стартапах» (минимум Фазы 1):

- **Zod** на границе HTTP (body/query) до вызова service.  
- **pino** для логов (дефолт Fastify).  
- OpenAPI/Swagger — **опционально после** CRUD, не блокер #34/#38.  
- Проверка env (`DATABASE_URL`, `PORT`) через Zod при старте — допустимый follow-up в #37/#38.

Не меняем без отдельного решения:

- `GET /health`;  
- dotenv из **корня** репо;  
- порт **3001**;  
- имя пакета `@dpline/api`.

### Путь к Nest (Фаза 2+)

Nest **не** внедряем rewrite in place в том же `apps/api`.

Триггер (что наступит раньше):

- старт **Фазы 2** (front shell), **или**  
- появление **auth**.

Способ переезда (**strangler**):

1. Новый пакет в монорепе (рабочее имя: `apps/api-nest`).  
2. Тот же Postgres / Prisma (или совместимый слой).  
3. Cutover: compose/env/порт → новый сервис; старый Fastify выключаем.  
4. Новый ADR со статусом **accepted**, эта ADR → `superseded by ADR-00N`.

Детали cutover — в ADR миграции, не здесь.

## Последствия

### Плюсы

- Быстрый CRUD и понятные слои для учёбы.  
- Практика Fastify + Zod + pino — переносимый навык.  
- Nest остаётся целью без давления «сделать всё сразу».

### Минусы и долги

- Два стека во времени (Fastify → Nest) — осознанная цена.  
- Нужна дисциплина слоёв, иначе снова god-`index.ts`.  
- `/gh-start-task` и merge-автоматизация не связаны с выбором фреймворка; код api появится в follow-up issues.

- Thin `node:http` как ядро после Prototype.  
- Nest **в том же app** «потихоньку переписать» без отдельного сервиса.  
- tRPC на Фазе 1.  
- Смена порта / отказ от root `.env` «заодно» с фреймворком.
