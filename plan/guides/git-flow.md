# Git flow в DPline

Уровень: «базу знаешь, практики мало». Это не учебник Git с нуля, а **как мы ведём ветки и PR**, зачем так делают в компаниях и где обычно ломаются новички.

Операционные правила (коротко) — в [working-agreement.md](../working-agreement.md). Здесь — теория и карта действий.

---

## 1. Зачем вообще ветки

История git — лента коммитов. Ветка — **указатель** на коммит + свобода наращивать историю, не ломая чужую линию.

Без веток все коммитят в одну линию → невозможно:

- спокойно экспериментировать;
- ревьюить изменения пакетом (PR);
- держать «то, что уже можно показывать» отдельно от «то, что ещё сырое».

**PR (Pull Request)** — предложение: «влить мою линию коммитов в целевую ветку» + обсуждение + CI + запись решения. В компаниях код почти никогда не пушат напрямую в `main`/`dev` без PR (исключения — крошечные hotfix по договорённости; у нас тоже лучше через PR).

---

## 2. Три слоя веток у нас

```text
main                 ← прод (default на сайте GitHub); стабильно, редко
  ↑ PR
dev                  ← интеграция завершённых кусков / фаз
  ↑ PR (в конце фазы или крупного эпика)
app-33-phase1        ← интеграция Фазы 1 (родитель #33); долгоживущая
  ↑ PR субтасков
app-34-adr-api-orm   ← субтаск (#34) от phase1, не напрямую от dev
```

| Ветка | Роль | Кто мержит куда |
|-------|------|-----------------|
| `main` | Прод; **остаётся default branch** на GitHub | Только из `dev`, когда сознательно решили выкатить |
| `dev` | Интеграция | Сюда — завершённые эпики/фазы (и обычные мелкие задачи вне эпика) |
| `app-<epic>-phaseN` / `app-<epic>-…` | Долгоживущая ветка эпика (напр. Фаза 1) | PR → `dev`, когда эпик/срез готов |
| `app-<n>-<label>` | Субтаск / обычная задача | PR → **ветку эпика** (если работа внутри фазы) или → `dev` (если задача сама по себе) |
| `pr-<n>-<label>` | Учебная практика | PR → `dev` (или в эпик, если так договорились) |

Формат имени **строго**: `{app\|pr}-{номер}-{label}` (kebab), примеры: `app-34-adr-api-orm`, `app-33-phase1`.  
Создание обычной ветки от `dev`: `/gh-start-task N`.  
**Внутри Фазы 1:** ветку субтаска создавать от `app-33-phase1`, не от `dev` (скрипт `start-task.sh` пока всегда от `dev` — для эпика делай вручную, см. §4).

**Почему не Git Flow Atlassian «как в учебнике»?** Классический Git Flow (`develop` + `release` + `hotfix`) тяжеловат для одного человека. Наш вариант ближе к **GitHub Flow + `dev` + опциональная ветка эпика** на длинную фазу.

## 3. Жизненный цикл одной задачи

1. Issue в Project → колонка **Ready** → берёшь в работу → **In Progress**.
2. Локально:

```bash
git checkout dev
git pull origin dev
git checkout -b app-12-web   # или: scripts/gh/start-task.sh 12
```

3. Коммиты (лучше мелкие, понятные). Conventional Commits:

```text
feat: …     новая возможность
fix: …      баг
docs: …     только документация / plan
chore: …    рутина (игноры, мелкий конфиг)
ci: …       пайплайн
refactor: … без смены поведения
```

4. Push ветки:

```bash
git push -u origin HEAD
```

5. PR в **`dev`** (не в `main`). В описании:

```text
Closes #12
```

или `Refs #12`, если issue ещё не полностью закрываем.

6. Project → **Review**. Читаешь diff сам (потом + Bugbot).
7. Merge (часто **Create a merge commit** или **Squash** — см. §6). Конфликты — не обходить force-push’ем в общую ветку.
8. Project → **Done**. Локально:

```bash
git checkout dev
git pull origin dev
```

Ветку задачи после merge можно удалить на remote (кнопка в UI PR) и локально: `git branch -d app-12fr`.

## 4. Подзадачи и ветка эпика (Фаза 1)

### Фаза 1 (Prototype, родитель #33) — договорённость 2026-07-27

```text
dev
  └── app-33-phase1          ← интеграция всех субтасков Фазы 1
        ├── app-34-adr-api-orm
        ├── app-35-ci-hygiene
        └── …
```

Как стартовать субтаск:

```bash
git fetch origin
git checkout app-33-phase1
git pull --ff-only origin app-33-phase1
git checkout -b app-34-adr-api-orm   # номер = issue субтаска
```

- PR субтаска: **base = `app-33-phase1`** (не `dev`), в теле `Closes #34` или `Refs #34`.
- Когда Фаза 1 / крупный срез готов: PR **`app-33-phase1` → `dev`**, в теле можно перечислить закрываемые issues.
- Workflow `on-pr-merged-dev` срабатывает на merge в **`dev`**. При merge только в `app-33-phase1` колонку Project для субтаска переводи в Done **вручную** (или дождись финального PR в `dev`).
- Периодически подтягивай `origin/dev` в `app-33-phase1`, если в `dev` появились нужные фиксы:  
  `git checkout app-33-phase1 && git merge origin/dev`.

### Обычные подзадачи (не эпик)

```text
dev → app-12fr
        → app-12fr-btn
```

Имеет смысл, если родительская ветка уже далеко от `dev` и подзадачу ревьюить отдельно.  
Иначе проще чеклист в одном PR.

Слияние: сначала PR подзадачи → в родителя, потом родитель → в `dev`.

## 5. Что такое конфликт и почему он появляется

Две ветки меняли **одни и те же строки** (или соседние так, что git не уверен). При merge/rebase git останавливается и просит человека выбрать итог.

Типичные причины у нас:

- давно не делал `git pull` на `dev` перед веткой;
- параллельно правил один и тот же файл в двух задачах;
- после merge в `dev` чужой PR затронул твой файл, а ты ещё не подтянул `dev` в свою ветку.

**Подтянуть свежий `dev` в свою ветку до финального PR** (привычка компаний):

```bash
git checkout app-12-web
git fetch origin
git merge origin/dev
# или: git rebase origin/dev  — см. §6
```

Разбор конфликта:

1. Открыть файлы с маркерами `<<<<<<<`, `=======`, `>>>>>>>`.
2. Оставить нужный итог (иногда — комбинацию обеих сторон).
3. Убрать маркеры.
4. `git add …` → `git commit` (если был merge) или `git rebase --continue`.

Пока мало практики — **merge предпочтительнее rebase**: история чуть шумнее, но проще откатить и понять. Rebase учим отдельно, когда merge уже не пугает.

Плохие идеи на старте:

- `git push --force` в `dev` / `main`;
- удалять чужие изменения «чтобы зелёное»;
- копировать файл целиком с одной стороны, не читая diff.

## 6. Merge commit vs Squash vs Rebase (практический смысл)

| Стратегия | Что получается в `dev` | Когда уместно |
|-----------|------------------------|---------------|
| **Merge commit** | Видна ветка + merge-узел | Учёба, прозрачная история «эта задача влилась вот тут» |
| **Squash** | Все коммиты задачи → один | Много мелких «WIP» коммитов, хочется чистый `dev` |
| **Rebase + merge** | Линейная история | Когда уже уверенно владеешь rebase |

Для DPline на Фазе 0: **Merge commit или Squash — оба ок**. Главное — единообразие на ближайшие недели; зафиксируем привычку в ADR, если станет больно.

---

## 7. `main` vs `dev` — дисциплина выкладки

- В **`dev`** можно сломать мелочь на день — это интеграционная ветка.
- В **`main`** — только то, что сам готов считать стабильным срезом.

Перенос `dev` → `main`: отдельный PR, когда есть смысл (например, после вертикального среза Фазы 0). Не каждый день.

Hotfix «только в main» пока **не закладываем** — чиним в ветке от `dev`, потом уже решаем, нужен ли срочный PR в `main`.

## 8. Связка с GitHub Project и Issues

| Событие | Project | Git |
|---------|---------|-----|
| Взял задачу | Ready → In Progress | создал ветку от `dev` |
| Открыл PR | → Review | PR в `dev` |
| Merge | → Done | `Closes #N` закроет issue |
| Сессия кончилась | поля Actual / заметка | **push** обязателен |

Issue без ветки = ещё не работа. Ветка без issue = работа без учёта (для нас плохо: Cursor и ты теряете нить).

Имя ветки **строго** `type-номер-label` (`app-12-web`). Label берётся из meta в теле issue (создаёт `/gh-create-task`).

## 9. Частые ошибки (и что делать)

| Ошибка | Почему плохо | Что вместо |
|--------|--------------|------------|
| Коммитить сразу в `dev` | Нет ревью, сложно откатить одну задачу | Всегда ветка + PR |
| Ветка от устаревшего `dev` | Поздние огромные конфликты | `pull` перед `checkout -b` |
| Одна ветка на 5 issues | Непонятно, что мержить | 1 issue ≈ 1 ветка |
| «Я потом залью» без push | Потеря при сбое диска / смена машины | Push до закрытия сессии |
| Force-push в общую ветку | Ломает историю другим (и себе) | Force только в *свою* feature-ветку, осознанно |
| Игнор CI на PR | Зелёный CI — часть Definition of Done | Чинить до merge (когда CI появится, #14) |

## 10. Минимальный чеклист перед «готово»

- [ ] Ветка от актуального `dev`
- [ ] Имя `app-…` / `pr-…` с номером issue
- [ ] PR в `dev`, в теле `Closes #N` или `Refs #N`
- [ ] Diff просмотрен тобой
- [ ] Конфликты разрешены осмысленно
- [ ] Project: Review → после merge Done
- [ ] Локально `git checkout dev && git pull`
- [ ] Push всего, что должно жить в remote

---

## 11. Что практиковать сознательно (навык)

Ближайшие тренировки не «выучить команды», а **пройти путь глазами**:

1. Melкая docs-ветка → PR → merge (`#16`).
2. Два раза подряд создать ветку, когда `dev` уже ушёл вперёд → merge `origin/dev` в свою → конфликт на md → разрешить.
3. Позже: один squash-merge, один merge-commit — сравнить `git log --oneline --graph`.

Когда упрёшься в конкретный экран GitHub или сообщение git — разберём **этот** случай, а не абстрактный учебник.
