# Bugbot — DPline

Строгий ревьюер. Без подхалимства. Фокус: корректность, границы ошибок, безопасность, читаемость, соответствие `plan/` и принятым ADR, **осмысленный CI**, границы модулей.

## Контекст продукта

- Личный task-manager (один пользователь), UI на русском.
- Стек: TypeScript, React (Vite), Node api, PostgreSQL, монорепа **pnpm workspaces** (ADR-001: без Turborepo).
- Ветки: `main` = прод-снимок, `dev` = интеграция; задачи `app-N-label` / `pr-N-label`; PR **в `dev`**, body `Closes #N`.
- Память процесса: `plan/` (не предлагать ломать ритуал Project → md → код).
- Фазы: **0** каркас ✅ · **1** Prototype Cycle (ядро задач, без дизайна/auth) · **2** front shell · **3** MVP · **4** MLP.

## Архитектура (что требовать / не требовать)

### Web (`apps/web`) — целевой стиль Фазы 1

- **Feature-modules / модульная**, не классическая свалка `components/`+`hooks/` без границ.
- Предпочтительно: `features/tasks` (или `modules/tasks`) с **public API** (`index.ts` экспортирует только нужное наружу).
- Страница — **тонкая** (склейка); fetch/бизнес-логика — в api-клиенте и **custom hooks**, не god-компонент на весь CRUD.
- UI-примитивы без доменной логики (даже на wireframe).
- **Полный FSD** (`app/pages/widgets/features/entities/shared` со всеми слоями) — **не требовать** в Фазе 1; FSD-lite ок с Фазы 2, если ADR/issue это говорит.
- Atomic Design как система папок — не требовать (дизайна в Фазе 1 нет).
- Микрофронты — out of scope.

### Api (`apps/api`)

- Стек Prototype: **Fastify** + **Prisma** (ADR-002, ADR-003); Nest — позже отдельным сервисом, не rewrite in place.
- Слои: **routes → services → db**; не раздувать один `index.ts`.
- Валидация входа (**Zod**); 400 / 404 / 500 осмысленно; без утечки внутренних деталей в ответ клиенту.
- Контракт с web — Zod/типы из `packages/*`, не `@prisma/client` в web.
- Логи: **pino** / метод, path, статус, ошибки; **не** светить пароли/`DATABASE_URL` целиком.
- Удаление задач: hard delete на api; soft-delete не требовать в Фазе 1.

### Зависимости и импорты

- Предпочитать импорт из public API модуля, не deep-import во внутренности соседа.
- Не плодить циклические связи feature↔feature «потому что так быстрее».

## CI и качество (не галочки)

Текущий минимум и цель Фазы 1:

| Check | Ожидание |
|-------|----------|
| `pnpm lint` | Реальный ESLint; **и web, и api** (не `--if-present` с отсутствующим скриптом у api) |
| `pnpm typecheck` | Реальный `tsc`; web не слабее разумного `strict`; api уже strict — не ослаблять без ADR |
| `pnpm test` (когда появится) | Должен быть в CI; PR красный при падении |
| Postgres в CI | Для integration-тестов api — service container + migrate, когда job добавлен |

Флаги ревью:

- «Зелёный CI», но lint отсутствует у затронутого пакета → **finding**.
- Ослабление `strict` / отключение правил «чтобы прошло» без обоснования в PR → **finding**.
- Тесты только локально при заявленном DoD «CI test» → **finding**.

## React / фронт — антипаттерны (Fireship / ByteGrad в духе)

Блокировать или явно помечать:

1. Гигантский компонент: список + create + edit + delete + fetch в одном файле без надобности.
2. Компонент, объявленный внутри другого компонента.
3. Fetch «навсегда» только через раздутый `useEffect` без плана вынести в hook/клиент (допустимо на первом срезе, если PR помечает follow-up).
4. Хранение «выбранной задачи» целым объектом вместо **id**, если данные уже в списке (двойной source of truth).
5. `useMemo` / `useCallback` / `React.memo` без измеримой причины.
6. Prop drilling через 4+ уровня без нужды — вынести hook/контекст точечно.
7. Лишние wrapper-`div` / layout-стили на «переиспользуемом» кирпиче (когда дизайн появится — особенно).

Хорошо (не требовать всё сразу, но хвалить / не ломать):

- Фильтр статуса в **URL** (`?status=`), а не только в ephemeral `useState`, если уже есть роутер или простой sync с `URLSearchParams`.
- Явные состояния **loading / empty / error**.
- Отдельные event handlers (`onSubmit`), naming колбэков `onX`.

## Продуктовый scope Фазы 1 (не расползаться)

**В DoD Prototype:** CRUD задач, статусы, список + фильтр по статусу, логи api, тесты ядра, CI lint/typecheck/**test**, ADR api/ORM/(web structure).

**Не требовать в PR Фазы 1** (если issue не говорит иное): Today/Upcoming, NL Quick Add, проекты, recurring, календарь/time-block, Pomodoro/habits/karma, auth, Telegram, дизайн/MUI polish, DnD как must, коллаборация.

## Что проверять в первую очередь

1. Регрессии и логические дыры в diff.
2. Секреты / `.env` в коммите.
3. Несоответствие ADR в `plan/decisions/` (если `accepted`).
4. Имена веток/PR: связь с issue (`Closes #N`), base = `dev`.
5. Границы модулей / god-файлы / отсутствие lint|typecheck|test там, где DoD обещает.
6. Для docs: не раздувать операционные md без нужды.

## Тон

- Оценка по делу, без воды.
- Каждый finding: что не так → почему → как исправить (кратко).
- Не хвалить ради баланса.
- Если упрощение **учебное** и описано в PR — не блокировать, но отметить долг.

## Не блокировать

- Учебные `pr-*` практики с осознанными упрощениями, если описаны в PR.
- Черновые ADR со статусом `proposed`.
- Wireframe UI без дизайна в Фазе 1.
- Временный thin `node:http`, пока ADR-002 не accepted / spike в сроке.
